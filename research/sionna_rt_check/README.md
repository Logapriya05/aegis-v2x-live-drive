# Minimal Sionna RT 30 GHz check — environment blocker, not a result

Status: **BLOCKED on this machine**. No radio map or LoS result was produced.
Nothing outside this folder was touched (isolated venv, no changes to
`index.html`, the 3GPP channel, the evaluation pipeline, results, configs,
or the Grafana/backend work).

## What's here

- `make_meshes.py` — generates plain `.obj` meshes with no external
  dependencies: a ground plane plus 4 box buildings forming a simple
  street-canyon crossing (`meshes/`, regenerated by running the script;
  ran successfully, independent of Sionna).
- `run_v2i_check.py` — the intended RT check: loads those meshes into an
  empty `sionna.rt` scene, sets 30 GHz, places one fixed RSU transmitter
  (6 m) and one vehicle receiver (1.5 m) on the road between the
  buildings, runs `PathSolver` for a LoS/path result and `RadioMapSolver`
  for a small path-gain map, saving `out/path_gain.npy`.
- `.venv/` — isolated virtualenv (Python 3.13.15) for this check only.
  Not committed (see `.gitignore` note below).
- `run_output.txt` — the exact captured output of the one real run.

## Blocker (reproducible)

```
cd research/sionna_rt_check
.venv/Scripts/python.exe run_v2i_check.py
```

fails immediately, inside `import sionna.rt`, before any scene/mesh code
runs:

```
jitc_llvm_init(): LLVM API initialization failed ..
ImportError: jit_init_thread_state(): the LLVM backend is inactive because
the LLVM shared library ("LLVM-C.dll") could not be found! Set the
DRJIT_LIBLLVM_PATH environment variable to specify its path.
```

**Root cause:** `sionna.rt` (v2.2.0) hard-requires one of three Dr.Jit/Mitsuba
"autodiff" compute backends — `cuda_ad_mono_polarized`, `metal_ad_mono_polarized`,
or `llvm_ad_mono_polarized` (see `sionna/rt/__init__.py`'s `mi.set_variant(...)`
call, confirmed by reading the installed package). There is no scalar/CPU
fallback for the `_ad_` variants Sionna RT needs (`mitsuba.variants()` on
this install lists `scalar_rgb`/`scalar_spectral*` too, but those aren't
autodiff variants and Sionna RT doesn't use them).

This machine has:
- No GPU (`nvidia-smi`: not found) → no CUDA backend.
- Not macOS → no Metal backend.
- No system LLVM install anywhere (searched `C:\Program Files`,
  `C:\Program Files (x86)`, `C:\ProgramData`, no Rust/cargo toolchain,
  no `llvmlite`) → the LLVM-JIT backend can't start either, since Dr.Jit
  needs the real `LLVM-C.dll` (the full LLVM-C API), which only the
  official LLVM distribution ships.

## How this could be unblocked (not done here — out of this task's scope)

Any one of:
1. Install the official LLVM for Windows release (ships `LLVM-C.dll`) and
   set `DRJIT_LIBLLVM_PATH` to its full path, or add its `bin/` to `PATH`.
   This is a system-level install, not something pip/the isolated venv can
   do, and wasn't done without asking first.
2. Run on a machine/VM with an NVIDIA GPU (CUDA backend) — the normal way
   Sionna RT is used in practice.
3. Run on Linux, where LLVM shared libraries are far more commonly already
   present (e.g. via `apt install llvm`), still without a GPU.

  `sionna==2.2.0`, `sionna-rt==2.2.0`, `mitsuba==3.9.1`, `drjit==1.5.0`,
  `torch==2.15.0` (CPU build) — no TensorFlow dependency in this Sionna
  version, unlike the legacy 0.x line.
- The actual `pip install sionna` into `.venv` completed successfully
  (exit code 0) — the Python package install itself is not the problem.
- `make_meshes.py` runs standalone and produces valid `.obj` files.
- Current `sionna.rt` 2.x API (confirmed against official docs,
  `nvlabs.github.io/sionna/rt/...`, for the parts used in
  `run_v2i_check.py`): `load_scene(None)` for an empty scene,
  `SceneObject(fname=..., name=..., radio_material=...)` +
  `scene.edit(add=[...])` to add custom meshes, `scene.frequency = <Hz>`,
  `PathSolver()(scene, max_depth=..., los=..., ...)`,
  `RadioMapSolver()(scene, cell_size=..., samples_per_tx=...)`.
  **Not yet exercised against the real installed classes** since import
  itself fails first — treat the script as the intended next step once
  the backend blocker above is resolved, not as verified-working code.
